## 1. What the problem says
Add `pair<KeyT,MappedT> subtree(map_bst &left, map_bst &right)` to `CP::map_bst`.
- If the tree is **empty**: do nothing at all and return `pair<KeyT,MappedT>()`.
- Otherwise:
  - move the root's **left subtree** into `left` (anything `left` held before must be deleted) and set `left`'s `mSize` correctly;
  - move the root's **right subtree** into `right` the same way;
  - **return the root's data**; afterwards the tree contains **only the root**.
- The moved subtrees must keep their **exact shape and data**.
- Full marks need **O(left.size() + right.size())**. Watch `left`, `right` and `parent` pointers.
- A spare `size_t process(node* n)` is provided for any helper you want. Edit only `student.h`; no I/O.
- Subtasks: 20% tree size ≤ 3, 30% left and right subtrees have equal size, 50% no extra condition.

## 2. What it really means
Cut the two edges under the root and give each piece its own tree object. No node is created or copied; only pointers change.

```text
before:            m                          after:   m          left          right
                  50                                   50          30            70
                /    \                                         /    \
              30      70          ──►                         20    40
             /  \
           20    40
   m.size = 5                                  size 1     size 3        size 1
```

Pointer changes (5 writes + 2 sizes + 1 size):

```text
left.mRoot  = root->left   (30)        30->parent = NULL
right.mRoot = root->right  (70)        70->parent = NULL
root->left  = root->right = NULL       mSize = 1
left.mSize  = count(30's subtree) = 3  right.mSize = count(70's subtree) = 1
```

## 3. What, why, how
- **Why not insert node by node into left/right?** Inserting the keys again costs O(k log k) or worse, and inserting in a different order would change the shape. Re-pointing keeps the shape for free.
- **What must be fixed after moving a subtree:**
  1. the new owner's `mRoot` points to it;
  2. its root's `parent` becomes `NULL`. `map_bst` uses `parent` to walk up (iterators, erase), so a stale parent pointing into `m` breaks `left` later;
  3. the old parent (our root) forgets it: `mRoot->left = mRoot->right = NULL`;
  4. sizes: `mSize = 1` for us; the moved trees need a count.
- **Counting the size:** we don't know how the m.size()−1 other nodes are split between the two sides, so count one side with a recursive `process(n)` = `1 + process(left) + process(right)`. That is O(left.size() + right.size()), exactly what the problem asks for. (Counting only one side and computing the other as `mSize − 1 − that` is also valid and slightly faster.)
- **Clear first:** `left.clear()` / `right.clear()` delete their old nodes. Do it **after** the empty check, because an empty `m` must not touch them.
- Order matters: save `mRoot->left` / `mRoot->right` before setting them to NULL.

## 5. Traps
- **Forgetting `parent = NULL`** on the moved roots: printing still looks right, but `checkParent()`, iterator `--`/`++` past the root, or erase in `left` later follow the stale pointer back into `m`.
- **Not clearing left/right:** their old nodes leak (and their old `mSize` is wrong if you only add).
- **Clearing for an empty tree:** the spec says "do nothing", so check `mRoot == NULL` first.
- **Leaving `mRoot->left/right` set:** `m` and `left` would share nodes, and both destructors would delete them (double free, which ASan reports).
- **Setting sizes by guessing** (e.g. `(mSize-1)/2`): only correct in the 30% subtask with equal sides.
- **Copying with `operator=` or re-inserting:** shape could change and it is slower.

## 6. Background
Lesson 07, section 5.4: **moving subtrees between trees** is pure pointer surgery: whenever a node gets a new parent, write **both** directions (parent→child and child→parent) and fix every owner's `mRoot`/`mSize`. The same checklist is used in BST Split, which re-links nodes along a path, and in List Merge / Split List for linked lists.

## 1. โจทย์บอกอะไร
ให้เพิ่ม `pair<KeyT,MappedT> subtree(map_bst &left, map_bst &right)` ในคลาส `CP::map_bst`
- ถ้าต้นไม้ **ว่าง**: ไม่ต้องทำอะไรเลย แล้วคืน `pair<KeyT,MappedT>()`
- ถ้าไม่ว่าง:
  - ย้าย **ต้นไม้ย่อยซ้าย** ของรากไปไว้ใน `left` (ข้อมูลเดิมใน `left` ต้องถูกลบทิ้ง) และตั้ง `mSize` ของ `left` ให้ถูก
  - ย้าย **ต้นไม้ย่อยขวา** ของรากไปไว้ใน `right` แบบเดียวกัน
  - **คืนข้อมูลในปมราก** หลังเรียกเสร็จ ต้นไม้นี้ต้องเหลือ **แค่ปมราก**
- ต้นไม้ย่อยที่ถูกย้ายต้อง **รูปร่างและข้อมูลเหมือนเดิมทุกประการ**
- ถ้าจะได้เต็มต้องเป็น **O(left.size() + right.size())** ระวังพอยน์เตอร์ `left`, `right` และ `parent`
- มีโครง `size_t process(node* n)` ให้ใช้ทำอะไรก็ได้ แก้ได้เฉพาะ `student.h` ห้ามอ่าน/พิมพ์ข้อมูล
- ชุดทดสอบ: 20% ต้นไม้ขนาด ≤ 3, 30% ต้นย่อยซ้ายและขวามีขนาดเท่ากัน, 50% ไม่มีเงื่อนไขอื่น

## 3. อะไร ทำไม อย่างไร
- **ทำไมไม่ insert ทีละโหนดลง left/right?** ใส่ key ใหม่ทั้งหมดใช้ O(k log k) หรือแย่กว่า และถ้าใส่คนละลำดับรูปร่างจะเปลี่ยน การย้ายพอยน์เตอร์ได้รูปร่างเดิมฟรี
- **สิ่งที่ต้องแก้หลังย้ายต้นไม้ย่อย:**
  1. `mRoot` ของเจ้าของใหม่ชี้ไปที่มัน
  2. `parent` ของรากต้นย่อยต้องเป็น `NULL` เพราะ `map_bst` ใช้ `parent` เดินขึ้น (iterator, erase) ถ้ายังชี้กลับไปที่ `m` จะทำให้ `left` พังทีหลัง
  3. พ่อเดิม (รากของเรา) ต้องลืมมัน: `mRoot->left = mRoot->right = NULL`
  4. ขนาด: ของเรา `mSize = 1` ส่วนต้นที่ถูกย้ายต้องนับ
- **การนับขนาด:** เราไม่รู้ว่าโหนดอีก m.size()−1 ตัวแบ่งไปซ้ายขวาอย่างไร จึงนับด้วย `process(n)` แบบเวียนเกิด = `1 + process(left) + process(right)` ใช้เวลา O(left.size() + right.size()) ตรงตามที่โจทย์ต้องการ (นับข้างเดียวแล้วคิดอีกข้างเป็น `mSize − 1 − ข้างนั้น` ก็ถูกและเร็วกว่านิดหน่อย)
- **ล้างก่อน:** `left.clear()` / `right.clear()` ลบโหนดเก่า แต่ต้องทำ **หลัง** เช็กว่าต้นไม้ว่าง เพราะถ้า `m` ว่างห้ามแตะสองต้นนั้น
- ลำดับสำคัญ: เก็บ `mRoot->left` / `mRoot->right` ไว้ก่อน แล้วค่อยตั้งเป็น NULL

## 5. จุดที่มักพลาด
- **ลืม `parent = NULL`** ที่รากต้นที่ถูกย้าย: พิมพ์ออกมาดูเหมือนถูก แต่ `checkParent()`, การ `--`/`++` ของ iterator ที่เดินผ่านราก หรือ erase ใน `left` ทีหลัง จะเดินตามพอยน์เตอร์เก่ากลับเข้าไปใน `m`
- **ไม่ล้าง left/right:** โหนดเก่ารั่ว (และ `mSize` เก่าผิดถ้าแค่บวกเพิ่ม)
- **ล้างทั้งที่ต้นไม้ว่าง:** โจทย์บอกว่า "ไม่ต้องทำอะไร" ต้องเช็ก `mRoot == NULL` ก่อน
- **ไม่ตั้ง `mRoot->left/right` เป็น NULL:** `m` กับ `left` จะใช้โหนดร่วมกัน แล้ว destructor ทั้งสองจะ delete ซ้ำ (double free ซึ่ง ASan จับได้)
- **เดาขนาด** (เช่น `(mSize-1)/2`): ถูกแค่ชุดทดสอบ 30% ที่สองข้างเท่ากัน
- **คัดลอกด้วย `operator=` หรือ insert ใหม่:** รูปร่างอาจเปลี่ยนและช้ากว่า
