## 1. What the problem says
F(0) = 0, F(1) = 1 and F(i) = F(i−1) + F(i−2). Read N (1 ≤ N ≤ 45) and print F(N). Samples: F(1) = 1, F(10) = 55, F(17) = 1597.

## 2. What it really means
The definition translates directly into a recursive function, and that function is correct. The problem is **speed**: the call tree repeats the same work over and over.

```text
                    fib(5)
              /               \
         fib(4)                fib(3)          ← fib(3) is computed twice,
        /      \              /      \            fib(2) three times, ...
    fib(3)    fib(2)      fib(2)    fib(1)
    /    \
fib(2)  fib(1)
```

The number of calls grows like F(N) itself: for N = 45 about 3.7 billion calls, far beyond 1 second.

:::hint Hint 1
How many *different* values fib(i) can be asked for? Only N + 1 of them.
:::
:::hint Hint 2
Keep an array `memo[i]`, initialised to −1. Before computing fib(i), look it up; after computing it, store it.
:::

## 3. What, why, how
- **What:** the two signs of dynamic programming are both here:
  - **optimal / exact sub-structure:** F(i) is built from smaller answers F(i−1), F(i−2);
  - **overlapping sub-problems:** the same smaller answers are needed many times.
- **Why memoization fixes it:** each fib(i) is computed **once**; later calls return the stored value in O(1). Total work: O(N).
- **How (top-down):** keep the recursive code, add "look up first, store after". This is usually the fastest way to turn a correct recursion into a fast one on an exam.
- **Bottom-up alternative:** fill F[0], F[1], …, F[N] in a loop, or keep only the last two values. Same O(N), no recursion.
- **Size check:** F(45) = 1,134,903,170 < 2³¹ − 1 = 2,147,483,647, so even `int` fits; F(47) would not. We use `long long` anyway.

**Trace** of the memo table while computing fib(6) (each value is computed at the moment its first call returns):

| i | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| order filled | base | base | 1st | 2nd | 3rd | 4th | 5th |
| memo[i] | 0 | 1 | 1 | 2 | 3 | 5 | 8 |

fib(6) calls fib(5) and fib(4). fib(5) goes all the way down and fills memo[2..5]. When fib(6) then asks for fib(4), it is already in the table: one lookup instead of a whole subtree.

## 5. Traps
- **Using 0 as "not computed":** works for i ≥ 1 because F(i) > 0, but F(0) = 0 would be recomputed. −1 is the safe marker.
- **Forgetting to store** (`return fib(i-1) + fib(i-2);` without `memo[i] =`): the table stays empty and the program is as slow as before.
- **Array too small:** `memo[45]` has indices 0..44; we need index 45, so declare 46.

## 2. จริง ๆ แล้วถามอะไร
นิยามแปลงเป็นฟังก์ชันเวียนเกิดได้ตรง ๆ และฟังก์ชันนั้นก็ถูกต้อง ปัญหาคือ **ความเร็ว**: ต้นไม้การเรียกทำงานเดิมซ้ำแล้วซ้ำอีก

```text

              /               \

    /    \
fib(2)  fib(1)
```

จำนวนการเรียกโตพอ ๆ กับ F(N) เอง: N = 45 เรียกประมาณ 3.7 พันล้านครั้ง เกิน 1 วินาทีไปมาก

## 3. อะไร ทำไม อย่างไร
- **อะไร:** ลักษณะสองอย่างของ dynamic programming อยู่ในข้อนี้ครบ:
  - **โครงสร้างย่อย:** F(i) สร้างจากคำตอบที่เล็กกว่า F(i−1), F(i−2)
  - **ปัญหาย่อยซ้ำกัน:** คำตอบย่อยเดิมถูกใช้หลายครั้ง
- **ทำไม memoization แก้ได้:** แต่ละ fib(i) ถูกคำนวณ **ครั้งเดียว** การเรียกครั้งต่อไปคืนค่าที่เก็บไว้ใน O(1) งานรวม O(N)
- **อย่างไร (top-down):** ใช้โค้ดเวียนเกิดเดิม เพิ่ม "เปิดดูก่อน เก็บหลังคำนวณ" นี่มักเป็นวิธีที่เร็วที่สุดในห้องสอบที่จะเปลี่ยนการเวียนเกิดที่ถูกต้องให้เร็ว
- **แบบ bottom-up:** เติม F[0], F[1], …, F[N] ด้วยลูป หรือเก็บแค่สองค่าล่าสุด O(N) เท่ากัน ไม่ต้องเวียนเกิด
- **เช็กขนาด:** F(45) = 1,134,903,170 < 2³¹ − 1 = 2,147,483,647 ใช้ `int` ก็พอ แต่ F(47) จะไม่พอ เราใช้ `long long` ไว้ก่อน

## 5. จุดที่มักพลาด
- **ใช้ 0 แทน "ยังไม่คำนวณ":** ใช้ได้กับ i ≥ 1 เพราะ F(i) > 0 แต่ F(0) = 0 จะถูกคำนวณซ้ำ −1 ปลอดภัยกว่า
- **ลืมเก็บค่า** (`return fib(i-1) + fib(i-2);` โดยไม่มี `memo[i] =`): ตารางว่างตลอดและโปรแกรมช้าเท่าเดิม
- **อาร์เรย์เล็กไป:** `memo[45]` มีตำแหน่ง 0..44 แต่เราต้องใช้ตำแหน่ง 45 จึงต้องประกาศ 46
