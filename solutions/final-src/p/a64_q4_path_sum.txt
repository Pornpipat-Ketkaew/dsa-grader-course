## 1. What the problem says
An undirected graph has n nodes (numbered 0..n−1, n ≤ 20) and m weighted edges (m ≤ 200, weights 1..1000). You get 8 values K₁..K₈ (each 1..20,000). For each one, print **YES** if some **simple path** (a path that never visits a node twice) has edge weights adding up to exactly Kᵢ, otherwise **NO**. A path may start at any node.

Input: `n m`, the 8 values K, then m lines `a b w`.

Sample: edges 0–1 (10), 0–2 (15), 1–2 (5), 0–3 (35); K = 10 20 … 80 → **YES YES NO NO YES NO NO NO**. Note 0→1→2→0 sums to 30 but repeats node 0, so 30 is NO.

## 2. What it really means
Generate every simple path, collect the sums, answer the 8 questions. A simple path is built one node at a time, never returning to a node already on it: that is backtracking with an `onPath[]` array, started from every node.

```text
    10           paths from 0:    0-1 = 10 ✓K   0-1-2 = 15     0-2 = 15
 0 ──── 1                         0-2-1 = 20 ✓K 0-3 = 35
 │ ╲    │        paths from 2:    2-0-3 = 50 ✓K
35  15  5        30 needs 0-1-2-0: not simple
 │    ╲ │        sums that exist: 5 10 15 20 25 35 45 50 55
 3      2        → 10 YES, 20 YES, 30 NO, 40 NO, 50 YES, 60 NO, 70 NO, 80 NO
```

There is no polynomial shortcut to hope for: with all weights equal to w, "is there a path of sum (n−1)·w" asks for a **Hamiltonian path**, a famous NP-complete problem. The limit n ≤ 20 is the hint that a search is expected, and the work is in making the search skip hopeless branches.

:::hint Hint 1
n ≤ 20 and you need paths that never repeat a node. Write the DFS that extends a path by one unused neighbour at a time, starting once from every node, and record every sum you see.
:::
:::hint Hint 2
Two cuts make it fast. (1) Stop everything as soon as all 8 queries are answered. (2) Before going deeper, ask: can this path still grow into any K that is still open? The path can gain at most the heaviest edge of each node not yet on it, so if no open K lies in [sum, sum + that bound], return.
:::

## 3. What, why, how
- **What:** `dfs(u, sum)` over simple paths, from every start node, answering queries as their sums appear.
- **Why a bound is safe:** every node added to the path is entered through one edge touching it, and that edge weighs at most `heaviest[v]`. So the path can never gain more than `restMax` = Σ heaviest[v] over nodes not on the path. If no unanswered K lies in [sum, sum + restMax], nothing below this call can answer anything.
- **How:**
  - Read the edges into adjacency lists; compute `heaviest[v]`; `restMax` starts as the sum over all nodes.
  - On entering a node, subtract its `heaviest` from `restMax`; on leaving, add it back (like `onPath`).
  - In `dfs`: first the bound check, then mark every open K equal to `sum` as YES, then try each neighbour that is not on the path.
  - Keep `unanswered`; when it hits 0, return immediately everywhere.
- **Why every start node:** a path's sum is the same in both directions, but the path must be generated from one of its two ends; starting from every node covers all of them.
- **Cost:** exponential in the worst case. With the two cuts, typical random inputs with n = 20 take well under a second; the measurements are in the "Verified" box.

## 5. Traps
- **Forgetting "simple":** a plain DFS with a global `visited[]` that is never cleared finds only one path per start. The mark must be undone when the DFS returns (backtracking), so other paths through the same node are still tried.
- **Allowing node repeats:** the 0→1→2→0 cycle would make 30 a YES.
- **A path of one node** has sum 0, and every K ≥ 1, so it never answers anything; it is just the start of the search.
- **The worst case is still exponential.** Our slowest random case (n = 20, m = 80, one K just below the longest path sum, so it is never found and never cut) took 3.4 s. A K that cannot be reached but is not ruled out by the bound forces the search through almost every path. Whether the grader data contain such a case is not known; the point is to understand why these inputs are slow, since no method avoids them completely.
- **Not stopping early** after all 8 answers: on dense graphs that is the difference between milliseconds and minutes.
- **Output:** 8 lines, in the order of the queries, words in capitals.

## 6. Background
Lesson 11. Path problems split sharply: shortest paths are easy (Dijkstra), but **longest** or **exact-sum** simple paths are NP-hard. For n ≤ 20 the general exact method is a bit-mask DP over (set of visited nodes, last node), 2ⁿ · n states; here each state would have to carry a whole set of reachable sums (20,001 bits), about 2²⁰ · 20 · 2.5 KB, far too much memory. That is why the backtracking with bounds is the practical answer. Compare [Day cover](#a66_q1a_day_cover) for the "try all subsets, prune by the best so far" pattern.

## 3. อะไร ทำไม อย่างไร
- **อะไร:** `dfs(u, sum)` บน simple path จากทุกปมเริ่มต้น ตอบคำถามเมื่อผลรวมของมันปรากฏ
- **ทำไมขอบเขตปลอดภัย:** ทุกปมที่ถูกเพิ่มเข้าเส้นทางเข้ามาทางเส้นหนึ่งเส้นที่แตะมัน และเส้นนั้นหนักไม่เกิน `heaviest[v]` เส้นทางจึงเพิ่มได้ไม่เกิน `restMax` = ผลรวม heaviest[v] ของปมที่ยังไม่อยู่บนเส้นทาง ถ้าไม่มี K ที่ยังไม่ได้ตอบอยู่ใน [sum, sum + restMax] ทุกอย่างใต้การเรียกนี้ก็ตอบอะไรไม่ได้
- **อย่างไร:**
  - อ่านเส้นเชื่อมลง adjacency list คำนวณ `heaviest[v]` และ `restMax` เริ่มเป็นผลรวมของทุกปม
  - เมื่อเข้าปม ลบ `heaviest` ของมันออกจาก `restMax` เมื่อออกก็บวกคืน (เหมือน `onPath`)
  - ใน `dfs`: เช็กขอบเขตก่อน แล้วตั้ง K ที่เปิดอยู่และเท่ากับ `sum` เป็น YES แล้วลองเพื่อนบ้านแต่ละตัวที่ไม่อยู่บนเส้นทาง
  - เก็บ `unanswered` ไว้ เมื่อเป็น 0 ให้ return ทันทีทุกระดับ
- **ทำไมต้องเริ่มทุกปม:** ผลรวมของเส้นทางเท่ากันทั้งสองทิศ แต่เส้นทางต้องถูกสร้างจากปลายข้างใดข้างหนึ่ง การเริ่มจากทุกปมจึงครอบคลุมทุกเส้นทาง
- **ต้นทุน:** แย่สุดเป็นเลขชี้กำลัง เมื่อมีสองจุดตัด input สุ่มทั่วไปที่ n = 20 ใช้เวลาไม่ถึงวินาทีสบาย ๆ ตัวเลขที่วัดได้อยู่ในกล่อง "ตรวจสอบแล้ว"

## 5. จุดที่มักพลาด
- **ลืมว่าต้อง "simple":** DFS ธรรมดาที่ใช้ `visited[]` ทั่วทั้งโปรแกรมโดยไม่ล้างเลย จะเจอเส้นทางเดียวต่อจุดเริ่ม ต้องเอาเครื่องหมายออกตอน DFS กลับ (backtracking) เส้นทางอื่นที่ผ่านปมเดียวกันจึงยังถูกลอง
- **ยอมให้ผ่านปมซ้ำ:** วง 0→1→2→0 จะทำให้ 30 กลายเป็น YES
- **เส้นทางปมเดียว** มีผลรวม 0 และทุก K ≥ 1 จึงไม่เคยตอบอะไร เป็นแค่จุดเริ่มของการค้นหา
- **กรณีแย่สุดยังเป็นเลขชี้กำลัง** กรณีสุ่มที่ช้าที่สุดของเรา (n = 20, m = 80 และ K ตัวหนึ่งต่ำกว่าผลรวมเส้นทางที่ยาวที่สุดนิดเดียว จึงไม่เคยเจอและไม่เคยถูกตัด) ใช้ 3.4 วินาที K ที่ไปไม่ถึงแต่ขอบเขตตัดไม่ได้บังคับให้การค้นหาวิ่งผ่านเกือบทุกเส้นทาง ไม่รู้ว่าข้อมูลของ grader มีกรณีแบบนี้หรือไม่ ประเด็นคือเข้าใจว่าทำไม input แบบนี้ถึงช้า เพราะไม่มีวิธีไหนเลี่ยงได้หมด
- **ไม่หยุดก่อน** เมื่อตอบครบ 8 ข้อแล้ว: บนกราฟหนาแน่นนี่คือความต่างระหว่างมิลลิวินาทีกับหลายนาที
- **output:** 8 บรรทัด ตามลำดับคำถาม เป็นตัวพิมพ์ใหญ่
